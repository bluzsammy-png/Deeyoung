Notification Architecture — Event-Driven, User-Controlled (§25–§26)
Events originate once on the shared bus — users never poll. Every notification deep-links to the exact screen (e.g., the pending approval card).
EVENT SOURCES
Signal events
new signal · high-confidence opportunity on watchlist
SENTINEL events
approval requested · trade executed · stop hit · target hit
Risk events
risk limit touched · daily breaker armed · emergency stop
System events
broker disconnected · data stale/unavailable · provider degraded
Catalyst events
major catalyst on held/watched symbol
Account events
login, security, subscription changes
→
EVENT BUS
Single fan-out hub
analytics, SENTINEL, and system workers publish; notification service subscribes
Correlation IDs
event → signal → order traceable end-to-end (§44)
Event → deep link mapping
every event type knows its destination screen
→
NOTIFICATION SERVICE
Dedupe & coalesce
one catalyst → one notification, not one per watched list
Importance threshold
user-set floor; low-importance events stay in center only
Preferences per event type
channel selection, watchlist-only alerts, opt-out
Quiet hours
respect user timezone; approvals still queue for morning review
Delivery state machine
queued → sent → delivered → opened / failed → retry (never pretend delivered, §55)
→
CHANNELS
Web Push (VAPID) PHASE 5
free infrastructure; works on desktop + Android Chrome today
Email PHASE 5
verification, approvals digest, receipts; free-tier provider
Mobile Push (FCM/APNs) PHASE 9
activates only when native shells exist (§25 addendum)
In-app Notification Center PHASE 5
full history, read state, filters — source of truth
